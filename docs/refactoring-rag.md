# RAG のステートレス化（ChromaDB → 事前計算 + numpy）

2026-07-25 実施。バックエンドから ChromaDB を外し、事前計算した埋め込みに対する numpy のコサイン類似度検索に置き換えた。

## なぜ ChromaDB を外したか

**主目的はメモリ削減ではなく、ステートレス化してデプロイ先の選択肢を取り戻すことだった。**

- ChromaDB は `persist_directory` による永続ディスクを要求する。このためデプロイ先が実質 EC2 に固定されていて、Cloud Run のようなサーバーレス環境に載せられなかった。t3.micro（1GB）ではメモリが足りず動作も不安定だった。
- 対象文書は学習指導要領解説の1本だけで、500字チャンクに割っても **659チャンク**しかない。この規模にベクトルDBは過剰。埋め込み行列は float32 で 659 × 3072 = 約7.5MB に収まり、リポジトリに同梱できる。
- 検索は行列積1回で済む。構築時に L2 正規化しておけば、実行時はクエリベクトルを正規化して `vectors @ q` を計算するだけでコサイン類似度になる。

副次的な効果として実行時依存から chromadb / langchain-community / pypdf が消え、イメージとメモリが大幅に減った（下記の計測結果）。また `reportlab` が完全に未使用だったことが判明したので削除し、それに伴って `fonts-ipafont`（reportlab で日本語PDFを出すための apt パッケージ）も孤児になったため削除した。

## 検索インターフェースは維持した

`retrieve(query: str, k: int = 3) -> list[str]` を公開しており、**任意のクエリ文字列で上位k件を引ける**性質は削っていない。

現状の呼び出しは「中学{grade}年生 {unit}」の9通りだけなので、固定の対応表に置き換えることも技術的には可能だった。それをしなかったのは、将来「講師の自由記述による要望」を受け取り、**その要望が指定学年の範囲を超えていないかを検証する**用途で意味的検索が必要になるため。この用途では事前に列挙できない任意のクエリが飛んでくる。

## 構成

| ファイル | 役割 |
|---------|------|
| `backend/scripts/build_index.py` | 開発時のみ実行。pypdf でPDFからテキスト抽出 → 500字/オーバーラップ50 でチャンク化 → Gemini `models/gemini-embedding-001` で埋め込み → L2正規化して保存 |
| `backend/app/rag/data/guidelines_vectors.npz` | 埋め込み行列（float32・659×3072・L2正規化済み・7.5MB） |
| `backend/app/rag/data/guidelines_chunks.json` | チャンク本文・ページ番号・出典情報（レビュー可能な整形済みJSON・0.83MB） |
| `backend/app/rag/retriever.py` | 実行時の検索。インデックスと embeddings クライアントをモジュールロード時に一度だけ初期化 |
| `backend/scripts/capture_baseline.py` | 移行検証用。ChromaDB 版の検索結果スナップショットを取得 |
| `backend/tests/fixtures/retrieval_baseline.json` | そのスナップショット。検索まわりを変更したらこれと比較する |

pypdf と langchain-text-splitters は `build` 依存グループに置いてあり、実行時イメージには入らない（`uv sync --no-dev` の対象外）。

設計上の判断がいくつかある。

- **クエリ埋め込みに `functools.lru_cache`**。現状のクエリは組み合わせが9通りしかないので、2回目以降はAPI呼び出しがゼロになる。
- **`_embed_query` は失敗時に例外を投げる**。`lru_cache` は例外をキャッシュしないので、一時的なAPIエラーが恒久的に焼き付かない。戻り値で失敗を表現すると失敗自体がキャッシュされてしまう。
- **インデックス欠損・埋め込みAPI失敗のどちらでも例外を投げず空リストを返す**。呼び出し側は context なしで生成を続行できる。理由は必ずログに残す。
- **インデックス構築はバッチ単位でチェックポイントを書く**。埋め込みAPIの無料枠にはレート制限があり、659チャンクの構築中に 429 で落ちる可能性がある。落ちても再実行すれば続きから再開する。

## 検証方法と結果

ChromaDB を削除する**前に**ベースラインを取得した。削除後では比較対象が作れないため。

`frontend/src/mathUnits.ts` の全学年×単元（9組）について「中学{grade}年生 {unit}」で上位3件を引き、本文とスコアの両方を保存。リファクタ後に同じクエリを numpy 実装で引いて比較した。

```
順位まで完全一致: 27/27 (100.0%)
集合として一致  : 27/27 (100.0%)
```

**チャンク数も 659 で完全に一致した**（Chroma コレクション 659 件 = pypdf + 同一 splitter の出力 659 件）。PyPDFLoader を pypdf 直呼びに置き換えてもテキスト抽出結果は同一だった。L2 正規化・task_type の扱いにバグはない。

唯一の差はページ番号が 0 始まり → 1 始まりになった点（PyPDFLoader は 0 始まりで記録していた）。本文は同一で、これは意図的な変更。

検索されたチャンクは単元と正しく対応している。

- 平方根 → pp.137-139「Ａ(1) 正の数の平方根」「√a×√b＝√a×b」
- 正負の数 → pp.47/70「数の範囲を正の数と負の数にまで拡張し」

縮退動作も実測で確認した。

| ケース | 結果 |
|--------|------|
| インデックス欠損 | ERROR ログを出して起動継続 |
| インデックス空で `retrieve()` | `[]` |
| 埋め込みAPI失敗 | WARNING ログ + `[]` |
| API復旧後 | 3件返る（失敗がキャッシュされていない） |

`POST /print/generate` は中1〜中3の全9単元 × `num_questions=5` で 9/9 成功。変更前後とも同じ。

## 計測結果

`fonts-ipafont` 削除後の最終状態。

| 指標 | 変更前 (ChromaDB) | 変更後 (numpy) |
|------|------------------|---------------|
| イメージサイズ | 1.75 GB | **644 MB**（-63%） |
| インストールパッケージ数 | 135 | **67** |
| メモリ（起動直後 idle） | 180.1 MiB | 183.5 MiB |
| メモリ（リクエスト後） | 230 MiB | **193.9 MiB**（-36 MiB / -15.7%） |
| rag_search 初回（cold） | 0.49-1.03s（+ retriever_build 0.07-1.00s） | 0.42-0.85s（平均 0.524s） |
| rag_search 同一クエリ2回目 | 0.503s（キャッシュなし） | **1-15ms（平均 5.1ms）** |

idle のメモリがほぼ変わらないのは、ChromaDB が遅延ロードでリクエストが来て初めてメモリを掴むため。差はリクエスト後に出る。

cold のレイテンシが大きく変わらないのは、どちらも Gemini embedding API の呼び出し時間が支配的だから。効いているのは2回目以降で、**0.503s → 5.1ms** になった。旧実装はリクエストごとに `get_retriever()` で embeddings オブジェクトを作り直していたためキャッシュが効く余地がなかった。

## 副産物: uvicorn 配下でログが全て失われていた問題

リファクタ中に、**uvicorn が root logger を設定しないため `app.*` の logger が出力を持たず、ログが全て捨てられていた**ことに気づいた。

影響は「検索結果を目視確認できない」だけではない。`retriever` がインデックスの読み込みに失敗したときの **ERROR ログも見えない**。つまり指導要領を参照できないまま問題を生成し続けていても気づけない状態だった。「指導要領準拠」がこのアプリの売りなので、これは看過できない。

`app/main.py` で `logging.basicConfig(stream=sys.stdout)` を設定して修正した。`retriever` はモジュールロード時にインデックスを読むので、**ルータの import より前**に設定する必要がある（後ろに置くと起動時のログが間に合わない）。

既存の `[PERF]` 計測ログが専用のロガーと StreamHandler を自前で持っていたのは、まさにこの問題を回避するためだったと思われる。
